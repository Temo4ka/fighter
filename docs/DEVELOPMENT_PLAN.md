# План разработки: боевой модуль Fighter

Статус: **согласован** (2026-10-01) · **фазы 0, 1 и 1.5 выполнены** (решение после фазы 1 — гибридное тело; подбор ощущений — впереди) · Репозиторий: <https://github.com/Temo4ka/fighter>

## 1. Цель

Сделать **модуль боя**: два бойца на арене, физически достоверное взаимодействие, статы
и снаряжение влияют на физику. Модуль войдёт в более крупный проект, поэтому:

- бой — это **библиотека** с чётким API: на вход конфигурация боя, на выход результат;
- приложение в этом репозитории — **песочница** для запуска и проверки боя:
  минимальное главное меню, бой, пауза, итоги;
- экранов прокачки и снаряжения здесь нет. Снаряжение и статы приходят в бой
  из конфигурации (JSON).

## 2. Принятые решения

| Тема | Решение |
|---|---|
| Режимы | локальный PvP на одной клавиатуре → ИИ → сеть (очень поздно) |
| Модель тела | **гибрид** (решение после фазы 1): таз и ноги управляются напрямую (контроллер + клипы), торс, руки и голова — физические на моторах; при нокдауне всё тело — ragdoll. Полный active ragdoll (c) отклонён: подпорки равновесия заметны, а подбор под разные статы не сходится |
| Физика | **Box2D v3** под собственной C++-обёрткой; ragdoll-контроллер пишем сами |
| Статы | сила (STR), ловкость (DEX), телосложение (CON); новые — вместе с магией/способностями |
| Снаряжение | обязательно; задаёт массу и броню частей тела |
| Сборка | **CMake** + FetchContent + `CMakePresets.json`; macOS и Windows (**MSVC**) |
| Отладка | отдельная **debug-сборка** с отладочной визуализацией вместо текстур (§3.5) |
| Тесты | **Catch2** |
| Конфиги | **nlohmann/json** |
| Камера | статичная; следование и зум — на будущее |
| Анимации | позы в JSON, которые моторы отрабатывают физически (фаза 1); рисованных кадров нет |
| Арт | **пиксель-арт в приоритете**, сравниваем со сглаженной графикой; источники — бесплатные наборы и генерация нейросетью; трек «Арт и ассеты» (§5) |
| Ревью | я ревьюю всё; крупное и важное — потом вы (см. §8) |

Любая **новая** библиотека сверх перечисленных — только после согласования.

## 3. Ключевые соглашения

### 3.1 Единицы и координаты
- Мир в **метрах**, **килограммах**, **секундах**, углы в **радианах**.
- Ось **Y вверх**, начало координат — центр арены на уровне пола.
- Перевод мир → экран делается **в одном месте** — в камере рендера (`sf::View`).
  Нигде больше пиксели не появляются.
- Box2D-типы (`b2Vec2`, `b2BodyId`, …) не выходят за пределы `src/physics/`.

### 3.2 Игровой цикл
```
loop:
  poll OS events → InputSystem (снимок команд на тик для каждого игрока)
  accumulator += frameTime
  while accumulator >= FIXED_DT:        # FIXED_DT = 1/60 c, Box2D substeps = 4
      combat.update(commands, FIXED_DT)  # логика → моторы → physics.step
      accumulator -= FIXED_DT
  alpha = accumulator / FIXED_DT
  renderer.draw(prevSnapshot, currSnapshot, alpha)   # интерполяция
```
- Порядок этапов явный, в коде. Никакой зависимости от порядка подписки на события.
- Симуляция детерминирована при одинаковом вводе (это задел под ИИ, реплеи и сеть).

### 3.3 Владение
- У каждого объекта **один владелец** (`std::unique_ptr`). Бойцы и арена принадлежат `Battle`.
- Модули держат **невладеющие** ссылки и указатели. `shared_ptr` — только при доказанной общей собственности.
- Подписка на события — RAII-токен, который отписывается в деструкторе.
- Композиция вместо наследования: у бойца есть `Rig` (тело), `Stats`, `Loadout`, `StateMachine`.

### 3.4 Рендер не трогает физику
Физика после каждого тика публикует `RenderSnapshot`: трансформы частей тела, HP,
таймер, состояние. Рендер читает **только** снапшоты. Так рендер не зависит от Box2D,
а интерполяция получается почти бесплатно.

### 3.5 Debug-сборка

Две конфигурации в `CMakePresets.json`:

| Пресет | Что внутри |
|---|---|
| `release` | оптимизация, текстуры, отладочного кода в бинарнике **нет** |
| `debug` | `-g`, ассерты, санитайзеры (ASan/UBSan на macOS), макрос `FIGHTER_DEBUG`, отладочная визуализация |

**Как устроено.** Любой модуль может отправлять примитивы в общий приёмник
`debug::DrawList` в **мировых координатах**: линии, стрелки, окружности, многоугольники,
точки, текст рядом с объектом. Каждый примитив относится к **категории**. Рендер рисует
список поверх сцены (или вместо неё). В release все вызовы `debug::draw*` компилируются в
пустоту, и примитивы не собираются.

```cpp
// example from rig: an arrow for the motor torque at a joint
debug::drawArrow(debug::Cat::Motors, JointPos, TorqueDir * Scale, "tau=12.4");
```

**Режимы экрана** (переключаются клавишами в debug-сборке):
- `F1` — только отладочные примитивы, **без текстур** (режим по умолчанию в debug);
- `F2` — текстуры + примитивы поверх;
- `F3` — только текстуры (как в release);
- `F4` — включить/выключить текстовую панель;
- `1`…`9`, `0`, `-` — включить/выключить отдельные категории (их 11);
- `F6` — образцы всех категорий (временно, пока не у всех есть реальные данные).

**Категории и цвета** (палитра задаётся в одном месте — `src/debug/palette.hpp`):

| Категория | Что рисуется | Цвет |
|---|---|---|
| Hurtbox | части тела, по которым можно попасть | зелёный (левый боец) / синий (правый) |
| Hitbox | ударные части **в активной фазе** удара | красный |
| Block | зоны блока | жёлтый |
| Static | пол, стены арены | серый |
| Joints | шарниры, пределы углов (дуги) | белый |
| TargetPose | «призрак» целевой позы поверх реальной — главное для настройки PD-моторов | полупрозрачный голубой |
| Motors | момент мотора в шарнире (стрелка / дуга) | оранжевый |
| Forces | силы и импульсы: импульсы попаданий | пурпурный |
| Velocity | скорости центров масс частей; контроллер таза (скорость, отбрасывание) | бирюзовый |
| Contacts | точки контакта и нормали, импульс контакта | ярко-красные точки |
| CoM | центр масс бойца и опорная точка | чёрно-белый крест |

**Текстовая панель:** FPS и время кадра, время шага физики, номер тика; для каждого
бойца — состояние машины состояний (сейчас — «стоит / нокдаун / встаёт»), контроллер таза
(скорость, отбрасывание), какие части физические, текущий клип и фаза, HP, жёсткость моторов,
физический профиль (масса, момент, gain, скорость ходьбы); журнал последних `HitEvent` (кто, чем,
куда, импульс → урон).

**Управление временем** — без него физику не отладить:
- `P` — пауза; `.` — один шаг физики вперёд;
- `[` / `]` — замедление и ускорение (×0.1 … ×1);
- `Backspace` — перезапуск боя с теми же конфигами (было `R`, но `R` — удар ногой у P1);
- `F5` — перечитать JSON (риги, позы, баланс) без перезапуска.

Для текста используется JetBrains Mono (OFL) из `assets/fonts/`.

Для проверок и баг-репортов: `fighter_app --screenshot shot.png [--frames N] [--mode debug|both|textures] [--showcase]`.

## 4. Архитектура и контракты модулей

```
src/
  core/      — цикл, время, логгер, математика (Vec2), события
  debug/     — DrawList, категории, палитра, панель, управление временем (только FIGHTER_DEBUG)
  physics/   — обёртка Box2D: World, Body, Joint, ContactEvents
  rig/       — тело бойца: контроллер таза, позы ног, PD-моторы корпуса, жёсткость, нокдаун
  anim/      — клипы поз, проигрывание, смешивание
  combat/    — Battle, Fighter, машина состояний, урон, раунды  ← публичный API модуля
  stats/     — Stats, Equipment, Loadout, расчёт физического профиля
  render/    — камера, отрисовка снапшотов, debug draw, HUD
  app/       — песочница: окно, главное меню, пауза, итоги, привязка клавиш
data/        — JSON: риги, позы/клипы, предметы, тестовые бойцы, баланс
tests/       — Catch2
```

Зависимости строго сверху вниз: `app → render, combat`; `combat → rig, stats, anim, physics`;
`rig → physics`; `render → core` (и снапшоты из `combat`). Обратных зависимостей нет.
`debug` зависит только от `core`, поэтому отправлять в него примитивы может любой модуль.

### Основные контракты (фиксируются в фазе 0, дальше меняются только через ревью)

```cpp
// combat — публичный API модуля (src/combat/battle.hpp, config.hpp, commands.hpp,
// events.hpp, result.hpp, snapshot.hpp); в волне 0 фазы 2 — по О.1–О.6
struct FighterConfig { std::string Name; stats::Stats Stats; stats::Loadout Loadout;
                       std::optional<float> StartHp; std::string RigId; };
struct BattleConfig  { FighterConfig Left, Right; ArenaConfig Arena; double RoundTimeSec; };
struct BattleResult  { Winner WinnerSide; BattleEnd End; double TimeSec;
                       std::array<FighterReport, 2> Fighters; };   // HP, hits per part, moves

struct PlayerCommands {            // input snapshot for one step
    float MoveX;                   // -1..1, world space
    bool  Up, Down, Block;         // block zone: getBlockZone()
    bool  Jab, HeavyPunch, BodyKick, LowKick;
};

class Battle {
public:
    explicit Battle(const BattleConfig& Config);
    void update(const PlayerCommands& LeftCmd, const PlayerCommands& RightCmd, double Dt);
    const RenderSnapshot& getSnapshot() const;
    std::span<const BattleEvent> getEvents() const;   // events of the last update()
    const std::optional<BattleResult>& getResult() const;
};

// stats -> physics (src/stats/stats.hpp)
struct PhysicalProfile {
    PerBodyPart<PartParams> Parts;   // mass and armor of each part
    float MotorMaxTorque;            // STR
    float MotorGain;                 // DEX: how fast a pose is reached
    float MaxHp;                     // CON
};
PhysicalProfile computeProfile(const Stats& BaseStats, const Loadout& Gear, const BalanceTable& Balance);

// physics -> combat (src/physics/events.hpp)
struct HitEvent { PartRef Attacker, Victim; Vec2 Point; float ApproachSpeed; float Impulse; };

// debug (src/debug/draw.hpp): empty inlines in release
namespace debug {
enum class Cat { Hurtbox, Hitbox, Block, Static, Joints, TargetPose,
                 Motors, Forces, Velocity, Contacts, CoM };
void drawLine  (Cat Category, Vec2 From, Vec2 To);
void drawArrow (Cat Category, Vec2 From, Vec2 Vec, std::string_view Label = {});
void drawCircle(Cat Category, Vec2 Center, float Radius);
void drawArc   (Cat Category, Vec2 Center, float Radius, float Angle0, float Angle1);
void drawPoly  (Cat Category, std::span<const Vec2> Vertices);
void drawPoint (Cat Category, Vec2 At, float Size = 0.04f);
void drawCross (Cat Category, Vec2 At, float Size = 0.12f);
void drawText  (Cat Category, Vec2 At, std::string_view Text);
void setPanel  (std::string_view Key, std::string_view Value);   // text panel line
void logEvent  (std::string_view Message);                       // event log line
}
```

### Изменения контрактов в фазе 1

Физический спайк потребовал нескольких изменений; все они — дополнения, старый код
не ломается (кроме копирования `Battle`).

| Контракт | Изменение | Зачем |
|---|---|---|
| `BattleConfig` | новое поле `std::filesystem::path DataDir = "data"` | бой читает риги, клипы и `combat.json` при создании; новый `Battle` = перечитанные файлы (F5) |
| `Battle` | новый метод `std::span<const physics::HitEvent> getHits() const` — попадания последнего `update()` | сценарные тесты и журнал попаданий; предшественник `getEvents()` фазы 2 |
| `Battle` | реализация спрятана за `std::unique_ptr<Simulation>`: только перемещение, **копировать больше нельзя** | мир Box2D нельзя копировать; заголовок не тянет physics/rig/anim |
| `Battle` | конструктор бросает `std::runtime_error`, если файл в `DataDir` отсутствует или испорчен | песочница при F5 оставляет старый бой и пишет ошибку |
| `PartTransform` (core) | новое поле `Vec2 Size` — размер части в её системе координат | рендер рисует плейсхолдер нужного размера, не зная рига |
| core | новая функция `findBodyPart(std::string_view)` — часть тела по имени | имена частей в JSON |
| `FighterView` | `Parts` теперь заполнен (все 13 частей); `Position` — точка на полу между стопами | рендер рисует тело по частям |
| `physics` | `World` (тела, формы, шарниры, `step`, `getHitEvents`, `drawDebug`), `Body`, `RevoluteJoint`; `HitEvent` и `PartRef` без изменений | обёртка Box2D (задача 1.1); Box2D-типы не выходят из `src/physics/` |
| данные | `data/rigs/humanoid.json`, `data/poses/{stance,walk,jab,kick}.json`, `data/combat.json`; неизвестный ключ в них — ошибка | все параметры настройки — в JSON (docs/TUNING.md) |

`BodyPart`, `PhysicalProfile`, `PartParams`, `BalanceTable`, `computeProfile` и `PlayerCommands`
не менялись. Прыжок, присед и блок в фазе 1 не реализованы: `Jump`, `Crouch`, `Block`
в `PlayerCommands` пока игнорируются.

### Изменения контрактов в фазе 1.5

Публичный интерфейс `Battle` и `FighterView` не менялся: состояние бойца («стоит / нокдаун /
встаёт») видно на debug-панели, а тесты проверяют его по позе (высоте головы).

| Контракт | Изменение | Зачем |
|---|---|---|
| `PhysicalProfile` (stats) | новое поле `float MoveSpeedScale` (от DEX) и `BalanceTable::MoveSpeedPerDex` (+3 % за очко) | скорость ходьбы = `walkSpeed` из данных × множитель от DEX (задача 1.5.1) |

| `physics` | `BodyType::Kinematic`; `Body::getType`, `moveTo`, `setTransform`, `setAngularVelocity`, `setCollisionMask`; `World::setBodyType`, `setStrikeMass`; `ShapeDef::CollisionCategory/CollisionMask`. Удалены `Body::applyForce`, `applyForceToCenter`, `applyTorque`, `applyLinearImpulseToCenter` (служили только подпоркам) | кинематические таз и ноги, нокдаун; Box2D-типы по-прежнему не выходят из `src/physics/` |
| данные | `humanoid.json`: новый список `kinematic`; в `control` удалены подпорки (`upright*`, `standHeight`, `height*`, `groundTolerance`, `footLevelHeight`, `walkForce*`, `walkCycleMinRate`, `walkStartSec`), добавлены `walkAcceleration`, `knockbackScale`, `knockbackDecay`, `knockdownSpeed`, `knockdownSec`, `getUpSec`, `knockdownStiffness`; `combat.json`: `bodyHalfWidth`, `separationSpeed`; `kick.json` — удар в корпус | все параметры — в JSON, перезагрузка по `F5` (docs/TUNING.md) |

показано в TUNING.md и на панели (`assist`). Настройка ощущений — совместно, перед точкой решения.

**Точка решения (вместе):** играем в спайк. Если ощущение устраивает, остаёмся на (c).
Если нет, ограничиваем (c) — жёсткие моторы, ragdoll только при сильных ударах — или
откатываемся к (b). Фаза 2 стартует только после этого решения.

**Решение (2026-10-02): гибрид, фаза 1.5.** В сеансе настройки разгон и ощущение удара понравились,
но подпорка вертикали бросается в глаза, а ослабить её нельзя: боец складывается, давя в соперника.
Главное — статы и снаряжение меняют массу и силу в широких пределах, и подпорки равновесия
и ходьбы пришлось бы подбирать под каждое сочетание. Физика остаётся там, где даёт ценность
(удары и реакции), и убирается оттуда, где только мешает (стояние, равновесие, ходьба).

**Принципы ощущения боя (О.7).** По ним идёт настройка на сеансах:

1. **Темп** — основа 2XKO, но медленнее и приземлённее: бой на земле, без подбрасываний и воздушных комбо.
2. **Скорость удара от DEX в коридоре** — не быстрее Street Fighter. Ориентир: джеб 0.15–0.20 с до
   активной фазы, сильный удар 0.3–0.4 с, DEX сдвигает на ±25 %. Отдельной нижней границы у удара нет (решение 2026-10-05): скорость задают тайминги клипа и коридор DEX.
3. **Реакция зависит от силы атакующего и телосложения жертвы** — через ступени реакции
   (импульс от STR; масса и стойкость от CON и снаряжения).
4. **Нокдауны редкие** — только сильные удары или накопление.
5. **Умеренный реализм** — правдоподобные реакции, но не радикально: допустимы неброские эффекты
   (короткая вспышка при попадании, лёгкая тряска камеры от сильного удара, пыль при падении).
6. **Короткие цепочки** (джеб → джеб → сильный при попадании) — да; длинные комбо и жонглирование — нет.
7. **Больше влияния арены, предметов и RPG-статов** — стены (О.11), оружие (О.12), выносливость (О.13).

**Блок по направлению.** Пока зажата кнопка блока, вертикальные клавиши выбирают зону, а не
присед. «Вперёд» — к сопернику (для правого бойца это влево).

| Ввод | Зона блока | Закрывает попадания в |
|---|---|---|
| блок + вверх | верх | голову |
| блок + вверх-вперёд, блок без направления | середина | торс и руки |
| блок + вниз, блок + вниз-вперёд | низ | таз и ноги |

Попадание в закрытую зону — урон снижен, реакция не выше «касания»; в открытую — как без блока.
Зону попадания бой берёт из части тела жертвы (`HitEvent::Victim.Part`).

   защиты не «уступают» по кругу.
2. **Стена, ходьба, позы** (агент, Opus, ветка `feature/walk-wall-blend`, параллельно с п. 1):
   одно плавное разведение бойцов, в том числе у стены; ноги шагают всегда, когда таз движется;
   смешивание поз при смене клипа, время перехода в JSON.
3. **Реакция таза и ног на удар** (после п. 1): таз кинематический и сейчас от удара только
   отъезжает по горизонтали — не наклоняется, не проседает, не «чувствует», куда пришёл удар;
   ноги не реагируют вовсе. Добавить отклонение таза от удара (наклон и проседание с пружиной
   и затуханием; сила — от импульса и точки попадания) и короткое «подламывание» колена от
   низкого удара — как добавку к позе, без отказа от кинематического таза. Параметры (сила,
   жёсткость, затухание, предел наклона) — в JSON, подбор на сеансе.
4. **Стоп-кадр при попадании** и, если понадобится, усиление отброса поверх физики.
5. ~~**Плейсхолдеры не совпадают по размеру с отладочными фигурами**~~ — решено: картинка ровно по форме части, без перекрытия у суставов (`--overlap` 0).
6. **Послойная ходьба** (агент, Opus, ветка `feature/layered-walk` от `integration/smoothness`):
   возврат в стойку после остановки выглядел плохо (стопа скользила в стойку). Решение пользователя
   (шаркающий шаг пока отклонён): ноги и верх тела — отдельные слои (`anim/layers.hpp`; какой слой
   играет клип — по его ключам). Остановившись, ноги доигрывают цикл только до ближайшей **широкой**
   фазы двойной опоры (`restMinFootSpread`) и замирают в ней — без скольжения и без перехода в
   стойку; это поза покоя, пока ноги не понадобятся, ходьба продолжается с той же фазы. Удары рукой,
   верхний и средний блок, реакции (включая `stagger` и `knockback` — их ключи ног убраны) ноги не
   трогают. Удар ногой, низкий удар, присед, низкий блок забирают ноги **настоящим шагом** за долю
   разгона (`legStep`): стопа отрывается, идёт по дуге и встаёт, другая стоит, таз не сдвигается,
   удар активен на том же тике. Переставленная стойка, `stopSlidesFeet`, `switchStepShare`,
   `stance_switched`, `slideFeet` и `footSlideSpeed` удалены. Классификация клипов, параметры и что
   видно в debug-сборке — TUNING.md, разделы 1 и 3б. Отложенный переход в стойку — не сейчас.
   Вопросы к настройке: поза покоя шире стойки (передняя стопа ≈ на 6 см дальше), и подошедшие
   вплотную бойцы стоят дальше друг от друга — их передние стопы встречаются; два шага в действие
   (стопа из воздуха + бьющая) укладываются в ≈ 0,07 с каждый — резко; `legStep.minDistance`,
   `liftHeight`, `startupShare`.
   **Продолжение (шаг идёт за нажатием).** Отзыв пользователя: шаги в удар и из удара хороши, но ходьба
   короткими нажатиями выглядела плохо — боец «садился», колени гнулись некрасиво. Причина подтвердилась:
   при отпускании таз почти сразу вставал, а ноги доигрывали до четверти цикла без пути таза; стоящая стопа
   оставалась на месте (до 0,25 м от позы), разницу гасили колено и опускание таза (короткие нажатия
   проседали на 10 см, ноги делали 0,76 м на 4 см пути таза). Решение пользователя реализовано: стоящая стопа
   стоит, переносимая идёт вместе с путём таза до места приземления (только пока клип держит её в воздухе),
   клип даёт высоту, наклон стопы и форму ноги; отпустил — таз докатывается до широкой двойной опоры не
   дальше `stopMaxCoast`, иначе шаг кончается коротким (стопа опускается, где есть, не ближе
   `shortStepMinSpread`); стопа дальше `legStep.restepDistance` от позы переступает шагом (не к сопернику
   ближе `legStep.restepClearance`); колено гнётся в свою сторону и не глубже `kneeExtraBend` сверх клипа,
   таз опускается к стопе не больше `maxPelvisDrop`; уход ног из действия ногами — переходом слоя ног.
   Вопросы к настройке: `stopMaxCoast` (сейчас короткие нажатия почти всегда дают короткий шаг),
   `shortStepMinSpread`, `stopResumeDistance`, `legStep.restepDistance` (поза ходьбы и так держит стопу до
   ≈ 0,1 м от клипа), `kneeExtraBend`, `maxPelvisDrop`; ходьба в приседе пока останавливается по-старому.
7. **Какая нога впереди после остановки** — решено: **зеркальная версия действия**. После остановки
   впереди может быть любая нога; если действию ногами нужна стойка, а впереди не та нога, для
   которой оно нарисовано, клип играет с поменянными ролями ног (`ThighL`↔`ThighR`, `ShinL`↔`ShinR`,
   `FootL`↔`FootR`, ударные части тоже), верх тела не зеркалится — перешагивать не нужно, тайминг и
   дальность те же. Прежний вариант (всегда нарисованная стойка, шаг меняет ноги) оставлен
   переключателем `legStep.stanceAfterStop`: `"mirror"` (по умолчанию) или `"authored"`.

выбирает удары по меткам и намерениям из данных, поэтому волна идёт до него.

Модель данных (предложение, фиксируется в М.1 на ревью):
- **Удар** (`data/moves/<id>.json`) больше не знает своей кнопки и оружия — только что он делает: клип,
  урон, выносливость, мин. реакция, клип вплотную, цепочки (теперь по id ударов), **метки** (`tags`:
  высота `high`/`mid`/`low`, вид `punch`/`kick`/`swing`/`thrust`… — по высоте работает блок, по меткам
  — реакции и ИИ) и **намерения** для ИИ (`ai`: рабочая дистанция, роль `poke`/`heavy`/`close`/`low`…,
  вес). Один удар можно дать нескольким оружиям.
- **Набор движений** (`data/movesets/<id>.json`): таблица «ввод → удар» и **блок**. Ввод — строка
  `"Forward+Heavy"`: направление относительно соперника (`Neutral`, `Forward`, `Back`, `Up`, `Down`,
  `UpForward`, `DownForward`, `UpBack`, `DownBack`) и одна или несколько кнопок. Выбор: точное совпадение,
  иначе цепочка запасных направлений из `data/input.json` (например `DownForward → Down → Neutral`),
  иначе набор-родитель (`inherit`: оружие наследует удары ногами от `unarmed`). Блок набора: какие зоны
  закрывает (щит — верх и середину сразу), доля урона сквозь блок, предел реакции, выносливость за
  принятый удар, клипы блока по зонам, части, которыми блокируют (оружие, щит, предплечья).
- **Предмет** (`data/items/`) — id, имя, занимаемые слоты и компоненты: `armor` (части, защита),
  `weapon` (набор движений, дальность, скорость, сила, рука `Main`/`Off`/`Both`), `shield` (форма,
  какие зоны закрывает), `shape` (геометрия на руке: длина, толщина, угол, хват, центр масс),
  `visual`. Слоты рук: `MainHand`, `OffHand`; двуручное занимает оба. Неизвестный компонент — ошибка
  загрузки. Набор движений бойца — от оружия в основной руке; щит или оружие в другой руке добавляют
  свои строки и блок (правило сложения — в М.1).
- **Проверка данных:** все перекрёстные ссылки (предмет → набор → удар → клип → ударные части,
  вводы без конфликтов, наследование без циклов) проверяются при загрузке и отдельной командой
  `fighter_app --check-data`; тест гоняет её по `data/`.
- **Стенд удара:** `fighter_app --stand <move> [--weapon <item>]` — удар раз за разом по манекену:
  траектория ударной части, активная фаза, дальность, длительности, F5 перезагружает удар и клип.
  Те же замеры — функцией для тестов и проверки данных.

**Готово, когда:** бойцы, снаряжение и арена нарисованы в выбранном стиле; у каждого файла
в `assets/` есть запись в `assets/LICENSES.md`; новая картинка подключается правкой
`data/visuals.json` без изменения кода.

## 6. Агенты фазы 2

Общие правила для всех агентов:
- работают **только в своих каталогах**; контракты (§4) меняют только через ревью;
- каждая ветка `feature/<агент>-<задача>`, PR в `main`;
- новая публичная функция → тест в `tests/<модуль>/`;
- не добавляют библиотек без согласования;
- **выводят отладочные данные своего модуля** в `debug::` (категории ниже); задача
  не считается готовой, пока её поведение не видно в debug-сборке;
- **коммитят часто, маленькими шагами** — каждый рабочий шаг сразу коммитом в своей
  ветке. Коммит дешёвый, а работа без коммитов теряется при сбое агента, и следующему
  приходится заново разбираться в чужих правках. Перед PR коммиты можно собрать
  в несколько логичных;
- **делают инженерную часть, а не подбор ощущений:** код, инструменты, тесты,
  параметры вынесены в JSON и перезагружаются по F5, каждый описан в `docs/TUNING.md`.
  Подбор значений, от которых зависит, как игра ощущается (баланс, ходьба,
  удары, жёсткость), ведётся вместе с пользователем, а не агентом в одиночку.
- **экономят вывод** (решение 2026-10-06): пока дорабатывают — запускают только нужные
  тесты (`ctest --preset debug -R "<имя>" --output-on-failure`), полный набор — перед
  коммитом, который завершает шаг; вывод сборки фильтруют (только ошибки и предупреждения
  или последние строки); большие файлы читают частями (сначала поиск, потом нужный кусок),
  только что изменённый файл не перечитывают; логи обрезают; скриншоты — только когда
  нужно проверить что-то визуальное. Без нужды не запускаем два агента на Opus
  параллельно на связанный код: их потом дорого сводить;
- **экономят токены** (решение 2026-10-07, касается и агентов, и основной сессии):
  - *тесты:* при доработке — только тесты задачи (`ctest -R`); полный набор — один раз
    перед завершающим коммитом, в отчёт идёт только итоговая строка. Долгие сценарные
    тесты помечаются тегом `[slow]` и запускаются перед слиянием; если цикл проверки
    дорогой (долгие сценарии, многократные прогоны), его отдают пользователю — готовой
    командой;
  - *сборка:* при доработке — только debug; release собирается и проверяется перед слиянием;
  - *меньше агентов:* небольшие задачи основная сессия делает сама — это дешевле агента
    (агент тратит 0,3–1,5 млн токенов). Агент — только для больших задач, по умолчанию
    Sonnet, Opus — для сложной физики и архитектуры;
  - *короткие отчёты:* итог агента — по шаблону, без пересказа кода; из этого плана агент
    читает только нужные разделы, а не весь файл;
  - *новая сессия:* после каждого слитого PR или законченной задачи основная сессия
    сохраняет состояние в память и отдельной строкой пишет «Пора начать новую сессию»
    (в длинной сессии каждый ответ дороже — заново читается вся переписка);
- **модель агента подбирается по сложности задачи** (таблица ниже). Если агент на модели
  попроще явно не справляется, задача перезапускается на Opus с его наработками.
  Ревью перед PR — всегда моё, на любой модели.

| Сложность | Модель | Задачи |
|---|---|---|
| сложная, рискованная: новая архитектура, физика, много связанного кода | **Opus** | фаза 1.5; A (физика и тело); C (рендер на списке отрисовки); D (машина состояний, урон); T.4 (пиксельный режим рендера) |
| средняя: понятная задача по готовому образцу, данные, интерфейс, тесты | **Sonnet** | B (клипы поз по готовому формату); E (формулы статов, `data/balance.json`); F (меню и экраны); T.2 (генератор плейсхолдеров) |
| механическая: поиск, учёт, оформление, однотипные правки | **Haiku** | T.3 (учёт лицензий); сводки и проверки по коду; переоформление документации |

Fable 5.1 — кандидат для сравнения с Sonnet на одной задаче средней сложности.

### A. Physics & Rig — `src/physics/`, `src/rig/`
Доводит гибридное тело фазы 1.5 до продакшена: стабильность физического корпуса при разнице
масс (тяжёлый доспех), события `HitEvent` с импульсом, управление жёсткостью из `combat`,
применение `PhysicalProfile` к сегментам, переходы «стоит → нокдаун → встаёт».
**Готово:** профиль с массой ×2 заметно тяжелее, но стабилен; тесты на детерминизм
(одинаковый ввод → одинаковые трансформы через N тиков).
**Debug:** Hurtbox, Static, Joints, TargetPose, Motors, Forces, Velocity, Contacts, CoM.

### B. Animation — `src/anim/`, `data/poses/`
Формат клипов (ключевые позы + тайминги), проигрывание, смешивание, события клипа
(«активная фаза удара»). Набор: стойка, ходьба, прыжок, присед, блок, джеб, удар ногой, получение удара, вставание.
**Готово:** все клипы описаны в JSON, переключаются без рывков, скорость клипа зависит от DEX.
**Debug:** в панели — текущий клип, фаза, вес смешивания.

### Общее правило событий (для D, C, F)
Внутри симуляции — данные, наружу — список событий шага: `Battle::getEvents()`,
рассылка через `Signal` в `App` (docs/ARCHITECTURE.md, «События»). Контракт зафиксирован
в волне 0 фазы 2 (2.0.1): src/combat/events.hpp.

### C. Render — `src/render/`
Камера (`sf::View`, метры → пиксели), отрисовка `RenderSnapshot` с интерполяцией,
cutout-спрайты на части тела (сначала цветные капсулы), debug draw, HUD (полоски HP, таймер).

**Рендер строится на списке отрисовки (render list)** — той же схеме, что отладочный
`debug::DrawList`:

```
RenderSnapshot ──► render::buildRenderList(Snapshot, Visuals) ──► RenderList ──► один общий цикл отрисовки
                                          ▲
                        data/visuals.json: часть тела / предмет / декорация → текстура, слой
```

- `RenderList` — набор общих примитивов: спрайт (текстура, положение, поворот, масштаб, слой),
  капсула, прямоугольник, полоска. Рендер умеет рисовать только их и ничего не знает об игре.
- Связь «объект → картинка» — **в данных** (`data/visuals.json`), а не в коде. Новая часть тела,
  предмет снаряжения со своим спрайтом или декорация арены — правка JSON, без изменений
  в цикле отрисовки.
- Порядок отрисовки задаётся слоем примитива (фон → арена → бойцы → эффекты), а не порядком
  вызовов в коде.
- Модуль боя по-прежнему не знает про SFML и текстуры: он отдаёт только снимок, текстуры
  к нему подбирает рендер.
- Новый **тип** примитива (например, частицы или эффект с шейдером) добавляется в `RenderList`
  и в цикл отрисовки один раз — это редкий случай.

**Готово:** при 60 Гц физики и 144 Гц экрана движение плавное; Box2D не включается;
бойцы и оружие рисуются спрайтами частей тела через список отрисовки, в HUD — HP, выносливость и таймер; привязка частей к текстурам —
в `data/visuals.json`.
Дальше развивает отрисовку debug-примитивов, заложенную в 0.9.

### D. Combat — `src/combat/`
`Battle`, машина состояний бойца (Idle / Walk / Jump / Crouch / Attack / Block / Hitstun / KO),
урон из `HitEvent` (импульс × броня части тела), блок, хитстан, таймер раунда, победа.
**Готово:** `Battle` проходит сценарные тесты без окна (скриптованный ввод → ожидаемый `BattleResult`).
**Debug:** Hitbox (только в активной фазе), Block; в панели — состояние бойца, HP, хитстан, журнал `HitEvent` → урон.
**События:** вводит `BattleEvent` и `Battle::getEvents()` по общему правилу выше; бой не вызывает подписчиков сам.

**Ступени реакции на попадание.** Поверх физической раскачки корпуса бой определяет ступень
реакции — она решает, что происходит с управлением. Сила удара считается как изменение скорости
жертвы, поэтому статы и снаряжение учитываются сами, а пороги одинаковы для всех бойцов:

```
сила (м/с) = импульс / масса жертвы × множитель места попадания × (1 − броня части тела)
```

| Ступень | Когда | Что происходит |
|---|---|---|
| 0. Касание | сила ниже порога 1 или удар в блок | только физическая раскачка, управление не теряется |
| 1. Вздрагивание | лёгкий удар | короткая потеря управления, небольшая просадка жёсткости |
| 2. Пошатывание | средний удар | дольше без управления, отбрасывание таза, клип «шаг назад» |
| 3. Отброс | сильный удар | ещё дольше без управления, большое отбрасывание, корпус почти обмякает |
| 4. Нокдаун | очень сильный удар | таз и ноги отпускаются, ragdoll, затем вставание (база — фаза 1.5) |

- **Накопление (стойкость):** удары подряд копятся и повышают ступень, накопленное спадает со временем;
  запас стойкости — от CON и брони.
- **Только повышение:** во время реакции новый удар может поднять ступень, но не понизить —
  иначе удар на границе порогов дёргает реакцию из-за разброса физики.
- **Данные:** пороги, множители мест попадания, длительности, отбрасывание и просадка по ступеням —
  в `data/reactions.json` с перезагрузкой по F5; значения подбираются вместе с пользователем.
- **Позже, по желанию:** контрудар (попадание в атакующего поднимает ступень на одну), отскок от стены,
  подброс.

**Готово (ступени):** сценарные тесты на каждую ступень — лёгкий удар не выше 1, серия лёгких
поднимает ступень, тяжёлый боец при том же ударе получает ступень не выше лёгкого, во время
реакции ступень не понижается. **Debug:** в панели — сила последнего удара (м/с), ступень,
стойкость; в журнале событий — `P1 jab → head: 1.8 m/s → stagger`.

### E. Stats & Equipment — `src/stats/`, `data/items/`, `data/balance.json`
Модель `Stats` (STR/DEX/CON), предметы (слот, часть тела, масса, броня), `Loadout`,
загрузка из JSON, `computeProfile()` по таблице баланса.
**Готово:** чистая логика, полное покрытие тестами; изменение баланса — только правка JSON.
**Debug:** в панели — статы и итоговый `PhysicalProfile` каждого бойца.
Может стартовать в фазе 1.

**Сделано (параллельно со спайком, ветка `feature/stats-equipment`):**
- каталог предметов `ItemCatalog` из `data/items/*.json` (id, имя, слот, части тела, масса, броня);
- `buildLoadout()`: снаряжение по списку id с проверками — неизвестный id, предмет дважды,
  два предмета в одном слоте, масса и броня вне диапазона, общая масса снаряжения;
- разбор и проверка `Stats` (каждый стат в [1, 30]);
- `FighterSheet` из `data/fighters/*.json` и `resolveFighterSheet()` → `Stats` + `Loadout`;
- примеры: 12 предметов (все слоты) и два бойца — `knight` (сила, тяжёлая броня)
  и `rogue` (ловкость, лёгкая);
- ошибки — `stats::DataError` с файлом, полем и значением в сообщении; тесты на каждую проверку.

**Ждёт спайка:** формулы `computeProfile()`, `PartParams`/`PhysicalProfile`
и загрузка `BalanceTable` из `data/balance.json` — спайк может их переделать.
Подключение `FighterSheet` к `combat::FighterConfig` и вывод в debug-панель — при интеграции.

### F. App & GUI — `src/app/`
Песочница: минимальное главное меню (Бой / Выход), выбор тестовых бойцов из `data/fighters/`,
пауза, экран итогов, раскладки двух игроков.
**Готово:** полный цикл меню → бой → итоги → меню без перезапуска.
**События:** после каждого шага рассылает `Battle::getEvents()` через `Signal`; экран итогов подписан на конец боя (`BattleOver`).

## 8. Процесс ревью

1. Агент заканчивает задачу → PR в `main`, CI зелёный.
2. Я ревьюю (корректность, контракты, тесты) и прошу правки.
3. **К вам на ревью** уходит PR, если он: меняет контракты §4, добавляет зависимость,
   больше ~300 строк или относится к фазе 0. Остальное я сливаю сам и пишу краткую сводку.
4. После каждой волны — короткий отчёт: что вошло, что осталось, какие риски.
